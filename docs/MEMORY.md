# KOVA — Decision Log

A record of decisions made while building the backend that aren't obvious
from reading the code alone, so future work doesn't accidentally relitigate
or contradict them. Append to this file as new non-obvious decisions get
made; don't remove old entries even if later superseded — note the
supersession instead.

## Fresh Supabase projects may need explicit GRANTs alongside RLS policies

Wiring this project up to a real (freshly created) Supabase project
surfaced a bug that no amount of static checking or unit testing could have
caught: every table access failed with `permission denied for table X`
(Postgres error `42501`), for both `service_role` and `authenticated`,
despite `0001_init.sql`'s RLS policies being logically correct. The cause:
**Row Level Security policies only ever narrow what a query can see or
touch — Postgres still requires an ordinary `GRANT` on the table before RLS
policies are even evaluated.** Supabase's dashboard-created projects
usually come with those grants pre-seeded for `anon`/`authenticated`/
`service_role` on the `public` schema, but this isn't something to rely on
for every project (template changes, project age, or an unusual creation
path can all affect it) — and there is no way to detect the gap short of
actually running a query against a real project. Two follow-up migrations
fix it explicitly rather than assuming it: `0004_service_role_grants.sql`
(`GRANT ALL ... TO service_role`, plus `ALTER DEFAULT PRIVILEGES` so future
tables inherit it) and `0005_authenticated_grants.sql` (grants scoped to
exactly what the `_select`/`_admin_write` RLS policies in `0001_init.sql`
already expect to gate). **Any new migration that adds a table other
migrations need to read or write must also grant the relevant privilege to
`authenticated` and/or `service_role`** — adding an RLS policy alone is not
sufficient, and the failure mode (a generic "permission denied") looks
identical to a missing or wrong RLS policy, which is what makes this easy
to misdiagnose.

## `queueMicrotask` around setState in scheduler.tsx's prop-reactive effects

`scheduler.tsx` has two `useEffect`s that don't run once on mount — they
genuinely need to re-run whenever the `driverBooking` or `reviewRecordId`
prop changes, recomputing the local `edit`/`date`/`tab` state from it. The
`react-hooks/set-state-in-effect` lint rule (added with the React
Compiler-era eslint plugin that ships with Next 16) flags any `setState`
called directly in an effect body, because in the common case that state
should instead be computed as a lazy `useState` initializer or derived
during render. That rewrite doesn't apply here — these two effects are not
one-time mount hydration, they're intentionally prop-driven — so the state
updates are wrapped in `queueMicrotask(() => { ... })` instead. This moves
the `setState` calls out of the effect body's direct/top-level statements
(satisfying the lint rule) while preserving the exact original behavior:
the effect still fires on the same dependency changes, and the state update
still lands before the next paint. **Do not "simplify" this by unwrapping
the `queueMicrotask` calls** — that reintroduces the lint error the wrapping
exists to avoid, and do not confuse it with the *other* fix used elsewhere
in the same file (lazy `useState` initializers), which only works for the
true one-time-on-mount cases.

## Auth identity: synthetic email per username

Supabase Auth requires an email for password sign-in, but KOVA's `accounts`
table (and the whole product) is username-based, with no email column. It
was tempting to add an `email` column instead, but that would introduce a
second identity the app doesn't actually need. Decision: every account's
Supabase Auth email is derived as `<username>@accounts.kova.internal`
(`lib/supabase/accounts.ts`, `usernameToAuthEmail`). This is invisible to
users and to the rest of the app — usernames stay the one identity that
matters. **Any code that creates or renames an Auth user must use this
helper**, never construct the email inline, or the two will drift.

## Vehicle records: client-generated id, server-side upsert

Unlike every other resource, a `VehicleRecord`'s `id` is generated by the
browser (`crypto.randomUUID()` in `app/scheduler.tsx`) the moment a Driver
opens a booking with no linked record yet — there is no
`POST /api/records`, only `PUT /api/records/:recordId`, and it's called for
both the very first save and every later save. The route therefore treats
`PUT` as an upsert, and — because `vehicle_records` also has a
`unique(date, plate)` constraint (one record per vehicle per day, covering
every booking for that vehicle that day) — it first checks for an existing
row by `id`, then falls back to checking by `(date, plate)` before deciding
whether to insert or update. This avoids a unique-constraint failure if a
Driver's browser generates a fresh id for a second booking against a
vehicle/day that another booking already produced a record for.

## `vehicle_records` writes: app code + service role, not an RPC

Every other write-heavy table in this schema (`bookings`, `booking_slots`)
grants zero RLS write policies and is only writable through a
`security definer` RPC function, by design (see the comments in
`0001_init.sql` and `0002_booking_functions.sql`). `vehicle_records` follows
the same "no direct policy" pattern, but as of this pass **no RPC was
written for it** — `app/api/records/[recordId]/route.ts` instead
re-implements the authorization/validation/history-diffing logic in
TypeScript and writes via the service-role client. This was a conscious
scope decision (the logic — submission validation, admin history diffing —
is much more naturally expressed in TypeScript than plpgsql) but it is
inconsistent with the rest of the codebase's pattern and has a narrower
atomicity guarantee. See `docs/TASKS.md` for the follow-up to reconsider
this.

## Vehicle plate rename needs its own RPC

Renaming a vehicle isn't a simple `UPDATE vehicles SET plate = ...` because
`bookings.plate` (and by extension `booking_slots.plate`,
`vehicle_records.plate`) reference it without `ON UPDATE CASCADE`, and the
product requires the old plate to keep resolving via `vehicle_aliases` for
historical records. A multi-statement client-side sequence could leave
these tables inconsistent if interrupted partway. Decision: added
`rename_vehicle` as a new `security definer` RPC
(`supabase/migrations/0003_vehicle_rename.sql`), following the exact same
pattern as the booking RPCs added in the previous migration, rather than
trying to force the rename through RLS-scoped direct table writes.

## Booking creation/editing/cancellation reuse the pre-existing RPCs

`create_booking`, `update_booking`, and `cancel_booking` already existed in
`0002_booking_functions.sql` before the API routes were written (added in an
earlier session alongside the schema). The routes in `app/api/bookings/**`
are thin wrappers that map the HTTP request/response shape onto these
functions and translate their Postgres error codes (`42501` -> 403,
`P0002` -> 404, `23505` -> 409, everything else -> 422) — no booking
business logic was re-implemented at the route layer, deliberately, so
there is exactly one place (the RPC) that can create a double-booking bug.

## Phase 2 security/perf hardening pass (2026-09-21)

A repo-wide audit (see `docs/TASKS.md`) surfaced and this pass fixed:

- **`PUT /api/records/:recordId` didn't verify a Driver's request `date`/
  `plate` matched the linked booking's actual `date`/`plate`** — only that
  `bookingId` referenced one of the Driver's own bookings. A Driver could
  therefore plant a fabricated `vehicle_records` row (including a forged
  `SUBMITTED FOR REVIEW` state) for a vehicle/day unrelated to any real
  trip. Fixed by adding `matchesBookingKey()` (`lib/supabase/records.ts`)
  and calling it before any write in the Driver branch.
- **`GET /api/bootstrap` never checked the `error` half of any of its six
  parallel Supabase queries** — a failing query silently rendered as empty
  data (e.g. "0 vehicles") instead of a visible error. Fixed by checking
  all six results before responding.
- **`is_admin()` was never revoked from `PUBLIC`**, so any authenticated
  user could call it directly (not just via RLS policy evaluation) to
  probe whether an arbitrary uuid belonged to an active Admin. Revoked
  from `PUBLIC`, granted only to `authenticated` (still required for RLS
  policies that call it, since policy evaluation checks the querying
  role's own `EXECUTE` privilege regardless of the callee being
  `security definer`).
- **Every `security definer` function used `search_path = public`**, which
  was already safe against the classic mutable-search-path hijack (it was
  fixed, not mutable) but not the stricter recommended form. All five
  (`is_admin`, `create_booking`, `update_booking`, `cancel_booking`,
  `rename_vehicle`) now use `search_path = ''` with every table reference
  schema-qualified as `public.<table>` — see `0006_harden_definer_functions.sql`.
- **RLS policies weren't split per-operation and called `auth.uid()`/
  `auth.role()` unwrapped**, re-evaluating per row instead of once per
  statement. `0007_rls_policies_per_operation.sql` splits every `for all`
  admin-write policy into explicit insert/update/delete policies (same
  predicates, so this is semantics-preserving, not a permission change)
  and wraps every auth function call as `(select auth.uid())`.
- **No indexes existed on any foreign-key or RLS-filtered column**
  (`bookings.driver_id`/`requested_by_account_id`/`created_by_account_id`/
  `plate`, `booking_slots.booking_id`, `people.account_id`,
  `vehicle_aliases.new_plate`, and the `(data->>'bookingId')::uuid`
  expression on `vehicle_records`) — added in
  `0008_indexes_for_rls_and_fks.sql`.

**None of migrations 0006–0009 change any table's columns**, so no
generated-types regeneration was needed (this repo hand-writes its
Supabase row types in `lib/supabase/mappers.ts`/route files rather than
using `supabase gen types typescript`, and that remains unaffected).

## Migrations 0006–0009 verified against a local `supabase start` instance (2026-09-21)

The Docker/WSL2 environment needed for local Supabase wasn't available when
the hardening pass above first shipped 0006–0008 (no Docker installed, then
no free disk space); once both were resolved, `supabase init` +
`supabase start` + `supabase db reset` were run and surfaced two real bugs
that pure code review had missed — both fixed in follow-up migrations
rather than by editing the already-applied-to-production `0001`–`0008`
(only `0006`, not yet applied anywhere, was safe to edit directly):

- **`revoke execute ... from public` never actually blocked `anon`.** This
  project's Supabase template applies `alter default privileges ... grant
  execute on functions to anon, authenticated, service_role` for functions
  created by `postgres`/`supabase_admin` — a grant to `anon` specifically,
  independent of `PUBLIC`. Every RPC (`is_admin` and all four booking/
  vehicle functions, including `create_booking`/`rename_vehicle` from
  `0002`/`0003`, years before this pass) was therefore still directly
  callable by `anon` despite their `revoke all ... from public`. Each
  RPC's own `auth.uid()` check denies an anon caller in practice (confirmed
  live: `set role anon; select create_booking(...)` → `ERROR: Not
  authorized to create bookings`), so this was never exploitable, but it's
  a real least-privilege gap. Fixed by adding an explicit `revoke ... from
  anon` alongside `from public` on every RPC (`0006`, amended in place
  since it had never reached production).
- **`search_path = ''` on `create_booking`/`update_booking` broke the
  `enforce_same_daily_driver`/`block_inactive_vehicle` triggers**
  (`0001_init.sql`) the first time an RPC call actually fired them
  (`ERROR: relation "vehicles" does not exist`). A trigger fired by a
  statement inside a function with `SET search_path` runs under that
  *overridden* search_path for the duration of the call — not the
  trigger's own default — so the triggers' unqualified `bookings`/
  `vehicles` references stopped resolving. Since `0001_init.sql` is
  already applied to production and must not be edited, this needed a new
  migration: `0009_fix_trigger_search_path.sql` gives both trigger
  functions their own `search_path = ''` and schema-qualified references,
  the same fix already applied to the `security definer` functions.

After both fixes, a full local regression pass confirmed against a seeded
Admin + two Drivers + a booking: `anon` sees zero rows on every table and
is denied every RPC/function call directly; a Driver sees exactly their
own booking and the shared accounts roster, and cannot write to `accounts`
(RLS `UPDATE 0`, silently no-opped, not an error — normal Postgres RLS
behavior); an Admin can write to `accounts` and see every booking;
`create_booking`, `cancel_booking`, and `rename_vehicle` all ran
end-to-end correctly (including `rename_vehicle` cascading a plate change
across `bookings` and `vehicle_aliases`, and the inactive-vehicle trigger
correctly blocking a new booking with a clean error rather than crashing).

**What this local pass does *not* cover**: it ran against a freshly reset,
empty database, so it did not — and could not — exercise
`0008_indexes_for_rls_and_fks.sql`'s expression index
`((data->>'bookingId')::uuid)` against pre-existing data. That index will
still fail to create if any real `vehicle_records` row has a non-UUID,
non-null `bookingId`. Check before applying `0008` to any project with
existing data:

```sql
select id, date, plate, data->>'bookingId' as booking_id
from vehicle_records
where data->>'bookingId' is not null
  and data->>'bookingId' !~ '^[0-9a-fA-F-]{36}$';
```

If that returns rows, resolve them (fix the data or adjust the index to
exclude them with a `where` clause) before running `0008` there.

## Docs vs. code as source of truth

`BACKEND_INTEGRATION.md` (repo root) was written *before* any backend code,
as the contract the frontend adapter (`lib/kova-api.ts`) was built against.
It remains the primary contract reference. `docs/DESIGN.md`'s API table is
a derived summary pointing at the implementing route files — if the two
ever disagree, treat that as a bug to fix, not a reason to trust one over
the other blindly; check which one the frontend actually relies on.
